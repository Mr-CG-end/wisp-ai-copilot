## 一、宿主页面卡顿：根因与优化方案

### 1.1 现象与已确认条件

用户反馈：插件生成回答期间，宿主网页持续卡顿。设备条件：WebGPU 后端 + 集成显卡。

### 1.2 排除项（不是原因）

- **面板渲染不影响宿主页面**。Side Panel 与宿主页面是不同的渲染进程，面板的 Markdown 渲染、打字机动画、流式刷新都跑在面板自己的主线程上，与网页主线程物理隔离。
- **Content Script 在生成期间不做任何事**。`entrypoints/content.ts` 注入页面的只有 `pagehide`、Navigation API 与 passive 的 `scroll` 监听，生成期间无持续运行的逻辑。

### 1.3 根因：GPU 争用（生成期间持续卡）

集显的 GPU 算力与内存带宽由推理和浏览器合成器共享。解码循环持续提交 GPU 计算，合成器拿不到足够时间片，表现为**整个浏览器**（不限于当前标签页）滚动掉帧、视频卡顿。

首个 token 之前的 prefill 是一次大批量 GPU 计算，上下文越长这一下卡得越明显，表现为「点击生成后先顿一下」。

### 1.4 优化方案（按性价比排序）

**A. 缩短上下文——对 prefill 顿挫最有效**

上下文长度直接决定 prefill 的 GPU 工作量，也决定每个解码 token 的 attention 计算量。`core/panel/performance.ts` 的省资源档已把摘要上下文压到 1000 字（均衡档 1400 字），方向正确。集显设备应稳定停留在省资源档。

**B. 修正档位初选逻辑——当前 `balanced` 实际不可达**

`core/panel/performance.ts:54` 的判据是 `deviceMemoryGb <= 8 || hardwareConcurrency <= 8`。但 Chrome 的 `navigator.deviceMemory` **规范上限就是 8**（取值集合为 0.25/0.5/1/2/4/8，再大的物理内存也报 8），因此该条件在所有 Chrome 设备上恒为真，初始档位永远是 `resource-saver`，`balanced` 只能靠生成后校准升上去。

需要明确意图：若本意是「一律保守起步、靠实测升档」，应删掉恒真的内存判据并把注释写清楚；若本意是让强机直接以均衡档起步，则判据写错了，应改用 `hardwareConcurrency` 与后端类型判断，或干脆等第一次实测结果。

**C. 关闭生成期间的打字机动画——减少面板侧的合成负担**

均衡档的 `animateStreamingText: true` 会在生成期间以 60fps 逐字推进 `visibleLength`（`TaskPanel.tsx:72-86`），每帧触发一次文本重排。面板虽是独立进程，但仍与网页共用同一个 GPU 进程做合成。

关键判断：流式输出**本身已经是逐步到达的**，28 tok/s 下文本增长已足够平滑，打字机动画是纯额外开销，并未带来可感知的体验增益。建议两档都关闭，或仅在 `tokensPerSec < 8`（WASM 档）时启用——那才是流本身不够平滑、需要动画补间的场景。

**D. 给集显用户一条「保页面流畅」的显式退路**

WASM 后端走 CPU 单线程推理（实测 8.2 tok/s），**完全不占用 GPU**，页面合成不受影响。对「宁可生成慢也要页面流畅」的集显用户，这是真正解决问题的选项。

这与既有设计一致：设计文档 §2.3 的后端选择红线要求 WebGPU 失败时由用户显式选择 WASM，Task 10 设置页已规划「模型后端」设置项。建议在设置项的 WASM 选项下补一行说明：`速度约为 WebGPU 的 1/3，但不占用显卡，网页浏览更流畅`——把这条退路从「故障兜底」升级为「集显用户的正当选择」。

**E. 缩短单次生成长度——缩短卡顿持续时间**

减小 `maxNewTokens` 不降低瞬时卡顿强度，但缩短其持续时间。省资源档已从 384/512 降到 256/320。

**F. 已知无效的方向（避免走弯路）**

在解码循环内插入让步（`setTimeout` 让 GPU 队列排空）在当前技术栈下**不可行**：`transformers.js` 的 `model.generate()` 是封闭循环，`StoppingCriteria._call` 与 `TextStreamer.callback_function` 均为同步回调，没有可 `await` 的 per-token 钩子。除非 patch 上游，否则无法在循环内主动让路。

### 1.5 顺带发现：正文提取的降级路径缺守卫（一次性卡顿）

`core/extract/article.ts` 用 `MAX_DOM_NODES = 12000` 防止 readability 处理巨型页面（第 40 行），但超限后走的降级路径 `heuristicText`（第 26-31 行）依然执行 `doc.cloneNode(true)` **全量克隆整个巨型 DOM**——上限挡住了 readability，却没挡住降级路径自身的成本。

该函数在宿主页面主线程同步执行，在数万节点的页面上会造成零点几秒到数秒的页面冻结。用户本次反馈的不是这个场景，但这是真实缺陷。

建议：降级路径改为不克隆整个 document，直接在原 document 上定位 `main`/`article`/`body` 后取 `textContent`，用选择器排除而非 DOM 删除来剔除 `script`/`nav` 等（或对超大 DOM 只克隆定位到的子树）。

## 二、设计文档需要修改的地方

`docs/Wisp_设计文档.md` 的主体问题是**契约层大面积滞后于实现**。以下按可信度分层。

### 2.1 已核实的漂移（三条，均为消息契约）

**D-1 · Port 消息契约过时（§2.1，文档 146-158 行）**

- `EXTRACT` / `GET_SELECTION` 实际携带 `epoch`（`core/messaging/types.ts:27-29`），文档无此字段
- `PanelToContent` 中的 `PING` 已移除，探活改走 runtime 消息（`types.ts:44`、`content.ts:18-21`）
- `EXTRACTED` 去掉顶层 `url`、新增 `method: 'readability' | 'heuristic'`（`types.ts:33-34`）
- 新增 `PAGE_NAVIGATED`（`types.ts:39`），用于 SPA 同文档导航失效——这条 SPA 路径是防串页闭环的重要补丁，文档完全没有

**D-2 · `ContentToBackground` 契约过时（§2.1，文档 160-164 行）**

文档中 `TOOLBAR_ACTION` 携带 `ctx: TaskContext`；实际改为携带 `{ action, text, url, lang }`，由 Service Worker 用 `sender.tab.id + epochs.get(tabId)` 权威组装 `ctx`（`background.ts:146-157`）。这是安全性上的改进——Content Script 不可信、也拿不到 epoch——但文档没有记录这个理由。另新增 `PING` 与 `PAGE_NAVIGATED` 两条消息。

**D-3 · SW ↔ Panel 消息集合过时（§2.1，文档 166-175 行）**

- `ACTIVE_TAB` 去掉 `url`（已在阶段二计划登记为有意偏差 B1，排期阶段末回写，**这一点不算失察**）
- `PENDING_ACTION` 新增 `id: Uuid` 用于双路径投递去重（`types.ts:58-59`）——不在 B1/B2/B3 任何一条内
- `PanelToBackground` 新增 `ENSURE_CONTENT_SCRIPT`、`TAB_CLOSED_CLEANUP`（`types.ts:49-53`）
- 新增四个 `sendResponse` 响应体类型 `ActiveTabInfo` / `EnsureContentScriptResult` / `PanelReadyResult` / `PendingActionEntry`（`types.ts:62-78`），文档完全未提这一整类「请求-响应」交互模式

> 注：即使阶段末按计划回写 B1/B2/B3 三处有意偏差，§2.1 仍会缺失上述大部分内容——三处偏差登记覆盖不了这些后续变更。

### 2.2 待核实但证据充分的漂移

**D-4 · 划词交付握手已从单路径变为双路径（§2.1 / §4.3）**

文档描述为「`PANEL_READY` → SW 回 `PENDING_ACTION` 并清空」；实际是收到 `TOOLBAR_ACTION` 就立即广播（面板已开的情况），`PANEL_READY` 另经 `sendResponse` 返回 `{active, pending}`，两路径靠 `id` 去重（`background.ts:122-131、146-164`）。另有 `sidePanel.open()` 失败时的 `OPEN_PANEL_HINT` 降级路径，该消息目前未纳入任何 union 类型。

**D-5 · Worker 推理契约三处字段缺失（§2.3）**

`LoadProgress` 新增 `pct`；`InitConfig` 新增 `cacheOnly`（缓存命中时的离线自动恢复，禁联网重下）；`getStatus()` 返回新增 `crossOriginIsolated` / `sharedArrayBufferAvailable` / `numThreads` 三个诊断字段。

**D-6 · `PanelState` 与实际 store 大幅不符（§3.3）**

`modelStatus` 从 5 态扩为 7 态（新增 `checking-cache`、`needs-user-choice`）；`backend` 改名 `modelBackend` 并新增 `downloadPct`；`page` 增 `ctx`/`text`/`method`；`currentTask` 增 `source`/`userInput`/`truncated`/`contextChars`；`error` 增 `retryable`。**最大结构差异**：store 里没有 `session` 字段，取而代之的是 `history: TaskHistoryEntry[]`，会话持久化由 `TaskPanel` 直接写 Dexie，不进 UI store。这个架构决策值得在文档里明说。

**D-7 · 性能档位机制在文档中完全没有对应（§2.2 / §3.3）**

新增的 `PerformanceProfile`（两档配置、设备信号初选、按 `GenStats + maxFrameGapMs` 运行时校准）不在任何 schema 或契约中。反过来，文档 §2.2 `Settings.outputLength: 'short'|'medium'|'long'` 从未实现——当前 `chrome.storage.local` 里只有裸键 `retentionDays`，仓库中不存在 `Settings` 接口的实现。两者职责重叠，需要裁决：档位机制是否取代 `outputLength`。

**D-8 · `PAGE_PERMISSION_REQUIRED` 错误码缺失（§5）**

实现中该码位列枚举首位（`types.ts:20`），用于区分「activeTab 未授权、需用户点工具栏图标」与「浏览器硬性禁止注入」两种情况，已在 `usePageChannel.ts:90、188` 实际分支处理。文档 §5 的枚举与异常矩阵均无此项。

**D-9 · F-01 初始化时序与已落地行为冲突（§4.1）**

文档时序图规定「用户确认下载 → init 内才查缓存」；M2 已落地的行为是「挂载后清单匹配即自动 cache-only 恢复，不显示确认按钮」，且 M2 实现计划把「缓存命中仍要求点击加载」列为阻断条件。§4.1 需拆成「首次下载」与「缓存自动恢复」两条路径。

**D-10 · 目录结构过时（§1.3）**

`core/` 下实际多出 `panel/`、`render/`、`bench/`；根目录不存在文档所列的 `components/` 与 `assets/`，UI 组件实际在 `entrypoints/sidepanel/components/`。

**D-11 · 隐身模式实现比文档更严格（§2.2）**

文档称隐身会话以 `incognito=true` 存于 Panel 内存；实际是隐身上下文直接不建会话对象（`TaskPanel.tsx:144` 提前 return null），`Session.incognito` 字段恒为 false、实际未使用。实现更保守，文档应向实现看齐。

**D-12 · 级联清理 API 比文档丰富（§2.2）**

`core/storage/cleanup.ts` 实际导出 `selectExpiredSessionIds` / `purgeExpired` / `purgeByTab` / `appendMessage`，文档只展示了 `purgeSessions` 加两行注释。

### 2.3 文档元信息与内部一致性

文档信息表仍写「状态：草案，等待阶段一技术验证回填实测数据」、更新日期停在 2026-07-22；而 §6 已填入全部实测值、§10 已判阶段门 Pass（回填发生在 07-24）。

**D-15 · 测试选型与阶段二计划冲突**

`InferenceProvider` 作为全应用唯一 Worker 持有者、`StreamMarkdown` 作为模型输出唯一渲染出口——这两项在 M2 实现计划中是硬约束且已落地，设计文档 §3.3 仍只泛写「Side Panel 拥有并创建 Worker」，§1.3 结构图也无此两文件。

### 2.4 一条需要澄清的「非问题」

设计文档 §8.2 的「Panel 用 Tailwind」与 UISpec、实现全部矛盾——但阶段二计划 §2.1 已将其登记为**有意偏差 B3** 并排期「阶段末回写」，阶段二尚未结束，因此这属于按计划推进中的待办，不是失察。同理 §2.1/§3.1 提到 `webNavigation.onCommitted`（偏差 B2），文档原文是「`webNavigation.onCommitted` / `tabs.onUpdated`」并列表述，实现选用了其中不需要额外权限的一路，与文档字面不冲突。

## 三、当前 UI 实现与 M2 UISpec 的偏差

### 3.1 已核实的高优先级偏差

**U-1 · 来源标识未做到常驻（高）**

UISpec §5.5 要求上下文栏「位于工具栏下方并始终可见」，§2 更把「只要存在页面快照，来源标识必须常驻」列为产品语义。但 `.wisp-page-bar`（`style.css:587-597`）无 `sticky`/`fixed`，而顶栏与底部提问栏都有——长输出或多轮历史滚动后，来源标识完全滚出视口，用户无法一眼确认「当前结果的依据是哪一页」。

修法：`.wisp-page-bar` 加 `position: sticky; top: 44px`（配 `z-index` 与不透明背景），或滚动后在顶栏下方保留一条压缩版来源条。

**U-2 · 流式期间渲染的是 Markdown 源码（高）**

`TaskPanel.tsx:88-97` 在生成期间渲染的是纯文本 `<span>{content.slice(0, visibleLength)}</span>`，用户会看到 `##`、`**` 等原始符号，直到完成瞬间才切换为 `StreamMarkdown`，造成版式跳变。

这不仅违反 UISpec §3.2「流式 Markdown」与 §5.7「保持清楚层级」，还与 M2 实现计划「`StreamMarkdown` 是模型输出唯一渲染出口」、阶段二计划「禁止直接渲染原始文本」两条硬约束冲突。全仓库未找到把此行为声明为性能取舍的记录。

**U-3 · 结果操作栏位置与规范相反（中）**

UISpec §5.7 要求「操作栏位于输出下方」；实现把停止/复制/重新生成全部放在 `.wisp-result-header`（输出上方，`TaskPanel.tsx:449-480`）。按钮内容本身合规，仅位置相反。需二选一：移到 body 之后，或修订规范认可顶部工具行。

**U-13 · muted 文字对比度不足（中）**：`--wisp-text-muted #697168` 坐在 `--wisp-bg #F2EFE7` 上实测约 4.39:1，低于 WCAG AA 的 4.5:1，且多用于 11-12px 小字。注意这是**规范自身的令牌与 §8 无障碍要求互相矛盾**，实现只是原样继承。修法：加深至约 `#5F675E`，或约束 muted 仅用于 `--wisp-surface` 背景（该背景上实测 4.83:1 达标）。

**U-14 · `aria-live` 范围过宽（中）**：`aria-live="polite"` 加在整个结果区容器上（`TaskPanel.tsx:432-437`），流式每 60ms 追加一次都会触发读屏播报，噪音极大。应收窄到状态行，正文容器不设 live region，完成时用 `role="status"` 播报一次。

**U-15 · 会话历史与 M2 禁令的边界不清（中）**：结果区已内联渲染多轮历史（`TaskPanel.tsx:100-121`，store 自动归档最近 20 条），而 UISpec §3.2/§9 写着「M2 不展示历史」「不得提前加入会话历史」。需要澄清该禁令仅指「跨会话历史浏览页」，并补上「当前会话多轮展示」的组件规范。

**U-16 · 取消/出错的输出归档后无状态标记（低）**：store 仅以 `streamBuffer` 非空判定归档、不看 status，历史条目也不渲染状态，导致被中断的半截回答与完整回答在展示上无法区分。

**U-17 · 横幅样式逐字重复（低）**：`.wisp-cross-tab-banner` 与 `.wisp-page-error-banner` 四段规则完全相同（含媒体查询内的成对规则），可合并为共享 class。

**U-18 · 微光轨迹用法越界（低）**：UISpec §4.3 限定品牌微光轨迹「只能出现在上下文栏与编辑器边注之间」，但初始化页有多处苔绿装饰线（`style.css:140-148、188-196`）。需澄清二者是否同一语汇。

**U-19 · 占位文本规范内部冲突（低）**：UISpec §5.3 写「基于本页内容提问…」，§5.8 写「基于这份快照提问…」，实现取了后者。规范需自我统一。

## 四、插件 UI 优化规划

### 4.1 规范空白区（M3/M4 马上要实现，但无规范）

**P-1 · 设置页与数据可见性规范（高）**

Task 10 已锁定设置页五组内容（模型后端 / 输出长度 / 数据用量 / 清除数据 / 隐私说明），但入口位置、导航模型、确认交互全部空白。建议：

- **入口**：顶栏右侧、运行状态之后，用**文字按钮**「设置」（满足「所有按钮使用可见文字」，也省掉图标资产）
- **导航**：单层推入视图，顶栏左侧变「返回」；不引入底部导航
- **内容**：全部复用既有 `.wisp-meta-list` 行样式；存储用量用文本行「约 412 MB · 会话 3 条 · 缓存 12 项」，不做图表或仪表盘
- **清除数据**：行内两步确认——点击后按钮原位变红实底「确认清除」+ 文字「取消」，5 秒未确认自动还原，不弹模态。这正是 UISpec §5.2「确认危险操作时才使用红色实底」预留的状态
- **隐身指示**：顶栏状态追加灰字「隐身 · 不保存」，设置页数据组显示一行说明
- **明文决策**：v0.1 不提供会话历史浏览界面，库内数据仅通过「数据用量」计数与「清除数据」可见可控——不写进规范，M3 途中极易临时长出历史入口

**P-2 · 划词工具条视觉规范（高）**

Task 11 对工具条样式只有一句功能性要求，颜色/尺寸/阴影/暗色宿主对策全部空白。关键技术事实：`--wisp-*` 令牌全声明在面板的 `:root` 上，**Shadow Root 不加载该文件**——不显式移植令牌，工具条会是一组无样式的默认按钮。建议：

- **令牌移植**：`selectionToolbar.css` 在 `:host` 上重新声明同值令牌，两处视觉同源
- **形态**：单行水平条，纸面底 + 1px 边框 + 8px 圆角 + UISpec §4.3 的弹层阴影（工具条是面板外唯一允许阴影的场景）；四个 28px 高文字按钮，悬停 `--wisp-accent-soft`，不用图标、不加分隔线
- **暗色宿主**：工具条自带纸面底色，深色网页上天然可读；规范明确「不跟随宿主主题」
- **手势退路提示**：`OPEN_PANEL_HINT` 复用同一容器样式，纯文字 + 3 秒消失
- 定位常量（选区下方 6px）与 z-index 写入规范，作为 Task 14 验收依据

**P-3 · 错误呈现分层矩阵（高）**

设计文档 §5 定义了 13 个错误码，Task 13 要求「统一走 StatusBanner」，但没人回答「哪个错误显示在哪里」。当前实现已自发分裂成三种呈现（页面级横幅 / 结果区内错误态 / 初始化整页态）。若机械地统一成一条小横幅，反而会把整页态错误降级、劣化体验。建议按影响面分四类逐码归位：

| 类别 | 呈现方式 | 错误码 |
|---|---|---|
| 整页态 | 替换主内容，沿用 ModelSetup 骨架 | `WEBGPU_UNAVAILABLE`、`OFFLINE_NO_MODEL`、`CACHE_CORRUPT`、`DOWNLOAD_FAILED`、`STORAGE_FULL` |
| 页面横幅 | 紧邻上下文栏，StatusBanner 的唯一职责 | `PAGE_INJECTION_BLOCKED`、`PAGE_PERMISSION_REQUIRED`、`PAGE_NO_CONTENT`、`TAB_CHANGED` |
| 结果区内态 | 保留已有输出 + 重试 | `WORKER_ERROR`、`WEBGPU_CRASH`，及 empty / cancelled 两个非错误终态 |
| 行内说明 | 非阻断 | `PAGE_TOO_LONG`（沿用 truncated-note 样式）、`DOWNLOAD_CANCELLED` |

每类固定标题字号、retryable 按钮位置、技术详情用 `<details>` 折叠。该矩阵同时兼作 Task 13 六态验收表的界面依据。

### 4.2 现有 M2 界面的优化

**P-4 · 性能档位退出「页面快照」信息行（高）**

在途改动把档位标签放进了上下文栏的字数行（`TaskPanel.tsx:396`），与「3,842 字」并列。但该行按规范只承载**页面快照事实**（域名/标题/字数/重新读取），档位是**运行时属性**。更要紧的是档位会在每次生成后被自动校准悄悄切换，直接改变送入模型的上下文预算（1000↔1400 字），埋在元信息行里用户几乎不会察觉。320px 下这个标签还会把 meta 行挤到第三行。建议：

- 档位标签从 `wisp-page-meta` 移除，页面栏回归纯页面事实
- 顶栏运行状态扩展为第三段：偏离默认时显示「本地 · WebGPU · 省资源」，均衡档不显示第三段——只在需要用户知情时发声
- Task 10 设置页增加「性能档位」行：自动（默认）/ 省资源 / 均衡，行下小字显示「当前自动判定：省资源」，手动选择后停用自动校准
- 自动切换不弹 toast，只更新顶栏文本
- 写进规范防回归：上下文栏的「已读取前 N 字」必须**始终等于本次实际送入模型的字符数**——这是档位对用户唯一必须可见的后果

**P-5 · 快照时效可见（中）**

「刚刚读取」是写死的静态文本（`TaskPanel.tsx:388`），读取 30 分钟后依旧显示「刚刚」。改为三档相对时间：`刚刚读取`（<1 分钟）→ `N 分钟前读取`（<1 小时）→ `今天 14:32 读取`，每分钟更新一次文本、不做动画，`title` 属性带绝对时间戳。store 的 `page` 增加 `readAt` 字段。措辞统一用过去式，符合「任何文案不得暗示仍在读取页面」的红线。

**P-6 · 边注编号跟随对话轮次（低）**

边注数字硬编码为「01」（`TaskPanel.tsx:439`），但结果区已渲染多轮历史，编号与内容不再对应。改为每轮递增 01、02…，改读新页后归零。「编辑感」这个关键词恰恰要求编号像文稿批注一样真实递增。

### 4.3 全局设计决策缺口

**P-7 · 深色模式显式定版（中）**

实现用 `color-scheme: light` 锁死浅色，UISpec 令牌只有浅色值，两者都没回答「浏览器深色主题下面板怎么办」——Chrome 深色主题时面板四周框架是深色，暖象牙页面会成为一块亮斑。建议 v0.1 **定版为「有意浅色」**并写入规范：纸张隐喻不随浏览器主题反转，深色等价方案列为阶段三评估项；同节附深色令牌草案备查（bg `#23261F` / surface `#2A2E27` / text `#E8E6DC` / accent 提亮至 `#8FAF9C` 以保 AA），明确即使做深色也仍是单一苔绿强调、无渐变无玻璃。唯一立即动作：Task 14 截图清单追加一张「深色浏览器主题 + 浅色面板」并排截图，确认边界处无对比度事故。

**P-8 · 扩展图标缺失（中，且影响功能）**

`wxt.config.ts` 完全没有 `icons` 与 `action.default_icon`，仓库也无图标文件——工具栏会显示浏览器默认拼图图标。而 Task 12 的手势退路文案是「请点击工具栏上的 Wisp 图标继续」，**依赖用户能认出这个图标**，退路可用性直接受损。建议：出一版极简图标（暖象牙圆角方底 + 苔绿 W 字标或一条微光轨迹曲线），16/32/48/128 四档 PNG 落 `public/icon/`；顺手把 manifest description 从「阶段一验证 / stage-1 inference spike」更新为产品描述。

favicon 占位（U-8）建议以实现的 30px 为准回改规范（30px 在 88px 高的上下文栏中比例更稳），并明文规定「不发起网络请求获取真实 favicon」——避免为此新增权限，守住四项权限红线。

**P-9 · 动效原则与 320px 基线（中）**

规范对动效只有两条零散规定，但实现已有两个无限循环动画（骨架屏脉冲、流式光标闪烁），新增的打字机动画还被绑进了性能档位——哪些循环被允许、打字机属「装饰」还是「状态反馈」，规范没有答案。建议新增「动效原则」节：

- 动效只允许表达进行中状态，装饰性动画为零
- 循环动画白名单仅骨架屏与光标两项，同屏至多一个循环元素（二者分属初始化与生成阶段，天然不共存）
- 过渡时长上限 180ms
- 打字机效果归类为**性能档位行为**而非动效，防止被当作装饰扩散到其他文本（另见 §1.4-C，建议直接关闭）

宽度侧：`body` 的 `min-width: 280px` 低于规范 320px 下限，280-319px 区间既无规范也无验收，建议对齐 320px；Task 14 的 320px 截图增补两项专项检查——meta 行不超两行、底部提问栏不遮挡结果区最后一行。
